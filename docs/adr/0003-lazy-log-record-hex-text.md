# ADR-0003：LogRecord 的 HEX 文本按需派生

- 状态：Accepted
- 日期：2026-10-23
- 决策范围：domain 记录模型与接收缓冲内存

## 背景

`LogRecord` 同时保存原始字节、文本和预生成的 `hex_text`。HEX 文本长度约为原始字节的 3 倍，而文本模式还会保留解码后的 `text`。发布验收测得：32 MiB 原始字节上限对应约 231 MiB 稳态私有内存，放大约 5.5 倍。

HEX 始终可以由 `raw` 完整派生，不需要作为权威状态长期保存；只有 CSV 导出和 HEX 显示会实际读取它。

## 候选方案

1. 继续预生成 `hex_text`，仅调整 32 MiB 缓冲上限：实现简单，但会改变用户可见的历史保留量，且没有降低单条记录成本。
2. 按估算内存重新计费缓冲：内存边界更准确，但会显著缩短同等上限下的记录历史，仍保留 3 倍 HEX 常驻成本。
3. 将 `hex_text` 改为按需计算的只读属性：记录只保存 `raw` 与 `text`，需要时再格式化 HEX。

## 决策

采用方案 3。

- `LogRecord` 不再声明 `hex_text` 字段，构造函数不再接受 `hex_text` 参数。
- `hex_text` 是只读属性，每次访问调用 `format_hex(raw)`，不在记录中缓存。
- 接收缓冲的 32 MiB 上限仍按原始字节计算，语义不变。
- CSV 日志、TXT 日志和 UI 继续通过 `record.hex_text` 读取，调用方无需改变读取方式。
- `raw` 仍是唯一权威数据源；`text` 因跨读取块补全字符无法总是从单条 `raw` 完整重建，继续存储。

## 后果

优点：

- 每条记录不再常驻约 3 倍原始字节的 HEX 文本，缓冲内存显著下降。
- 记录对象更小，序列化与复制成本降低。
- HEX 格式只由 `format_hex()` 一处定义，不存在存储值与原始字节不一致的可能。

代价与约束：

- 每次读取 `hex_text` 都会重新生成字符串；CSV 导出和 HEX 显示会产生临时对象，属于可接受的按需成本。
- 公开构造契约发生变化：直接向 `LogRecord` 传 `hex_text` 的调用方需要移除该参数。当前版本内部没有这种调用方式。
- `dataclasses.asdict()` 和 `repr()` 不再包含 `hex_text`，需要导出 HEX 时显式读取属性。

## 验证

- 单测断言 `dataclasses.fields(LogRecord)` 不含 `hex_text`。
- 单测断言 `from_bytes()` 构造期间不调用 `format_hex()`，首次访问 `hex_text` 时才调用并返回正确结果。
- 全量 pytest、Ruff 与文档同步检查通过。
