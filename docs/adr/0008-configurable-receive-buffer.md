# ADR-0008：可配置接收缓存上限

- 状态：Accepted
- 日期：2026-10-23
- 决策范围：AppConfig、RecordBuffer、SessionManager 与主窗口菜单

## 背景

接收缓存固定为 `100,000` 条或 `32 MiB` 原始字节。不同用户的内存预算和会话数量差异较大：长时间高速接收需要更大历史，多标签或低内存环境则希望降低占用。固定值无法覆盖两类场景。

## 候选方案

1. 保持固定值，只修改常量：实现最简单，但每类用户都要改代码或重新打包。
2. 在菜单中提供固定档位，并持久化到全局配置：兼顾可发现性与可控边界。
3. 提供任意字节数输入：灵活，但容易误设过小/过大，增加校验和界面复杂度。

## 决策

采用方案 2。

- 档位为 `16 MiB`、`32 MiB`、`64 MiB`，默认 `32 MiB`。
- `AppConfig` 新增 `receive_buffer_bytes`，允许 `1 MiB..512 MiB`；旧配置缺失时按默认值迁移，不提升 schema 版本。
- `SessionManager` 保存默认上限；新建会话用该值创建 `RecordBuffer`，修改时更新全部现有会话。
- `RecordBuffer.set_max_bytes()` 调整上限并立即从最旧记录开始淘汰，累计 `dropped_records` 只增不减。
- 菜单“接收缓存”子菜单为互斥选项，切换后立即生效并触发配置保存。
- 该上限只约束内存历史，不改变自动日志、手动导出或 UI 最近 2000 条渲染上限。

## 后果

优点：

- 用户可在不重启、不重新连接的情况下调整内存占用和历史长度。
- 设置随全局配置恢复，界面有明确档位，避免任意值误用。
- 现有 `RecordBuffer` 的淘汰和统计语义保持不变。

约束：

- 调小上限会立即丢弃最旧记录，属于不可逆操作；界面不额外确认，因为只影响内存显示历史，不影响已写入的自动日志。
- 修改上限会让所有会话的 `dropped_records` 增加，状态条中的淘汰计数可能跳变。
- 新增配置字段需要保持向后兼容；未来若改为任意值输入，需要单独的 UI 校验。

## 验证

- 模型测试覆盖默认值、三个档位和非法值。
- 缓冲测试覆盖缩小时淘汰、扩大时不淘汰。
- 管理器测试覆盖新建会话与现有会话同时更新。
- UI 测试覆盖菜单三项、默认勾选、切换后所有标签生效及配置持久化。
- 全量 pytest、Ruff 与文档同步检查通过。
